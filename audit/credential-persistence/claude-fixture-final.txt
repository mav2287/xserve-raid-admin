### Blocker: the mutant fails on `keys`, not `monitor-source`

`validate` (`CredentialPersistenceObservation.java:36`) checks the key set before it checks the `Attributes` value. The first case of the first loop has a null monitoring password and a non-null management password, and the first loop runs against the mutant jar.

According to `audit/static-inventory.json:23039-23057`, `toPrefsContainer` calls `getMonitoringPassword` once and then makes one `Map.put`. Your positive oracle expects `Attributes` to be missing when the monitoring password is null, which means that `put` only happens when the value isn't null. In the mutant, the getter returns the non-null management password instead, so `Attributes` gets added, and the `keys` check fails before `monitor-source` is ever reached. The fixture then prints `fixed_code=assertion_or_execution`, which doesn't match the oracle at `check_credential_persistence.py:102`, so the run stops with "Wrong-getter negative control failed".

If `put` actually ran unconditionally, the positive run would fail at `keys` instead. Either way, the fixture can't pass as written. I couldn't confirm which case applies because there's no disassembly of `SOMLocalizer` in the repo, but the reasoning holds in both cases.

**Fix:** in `validate`, move the `monitor-source` check above the `keys` check. That way, the null-monitor case fails with `monitor-source` (the getter returns the management value, not null), and the positive run is unaffected.
