**Inference from how the JDK 8 HotSpot verifier works:**

- With no `StackMapTable`, there's no stale frame that could still declare slot 2 as an `OutputStreamWriter`. The inference verifier works out the local types itself, and `-Xverify:all` already runs the only verifier that applies.
- If there is a `LineNumberTable` or `LocalVariableTable`, it stays byte-identical. Entries that now point inside 8–46 are debug metadata. The old verifier only checks that they're in range.

**Empirical:** under `-Xverify:all`, all 16 positive runs pass. All 16 negative controls fail at the expected `AssertionError`, with stderr matching exactly, so none of them failed with a `VerifyError`.

## Remaining defects (none block; ranked)

1. **The helper's method-call list misses interface calls.**
   - The regex at `check_preference_io.py:61` needs the form `invoke\w+ #N // Method`. javap prints `invokeinterface #N, k // InterfaceMethod …`, so those calls never match.
   - A mutant calling `((Closeable)writer).close()` or `Flushable.flush` would get past both the required check and the forbidden check (`:63` only names `Writer` and `OutputStreamWriter` `.close`).
   - The helper's hash (`51d208`) and the behaviour tests already cover this, so it's an extra layer, not a gap.
   - *Fix:* capture `(?:Method|InterfaceMethod)` with an optional `, k`, then assert that the whole multiset of calls equals a literal expected list. That one assertion replaces the separate required, close and forbidden checks.

2. **The new guards in `check_disassembly` have no unit negatives, and they check more than `store`.**
   - *Scope:* the version, `StackMapTable`, branch-into-window and slot-2 guards scan from `store` to the end of the class (`:49`), not just the `Code` of `store`. That direction fails closed, so it's safe.
   - *Opcodes:* the branch regex skips `jsr`, `jsr_w`, `tableswitch` and `lookupswitch`.
   - *No negatives:* `test_preference_io.py:40` damages only `after`, so failures there come from the comparison of the two disassemblies, not from the new guards. Nothing shows the new guards match real javap output and actually fire.
   - *Fix:* in `test_independent_complete_disassembly`, add these cases:
     - `before`/`after` both containing `47: goto 20`;
     - both containing `51: aload_2`;
     - `major version: 50`;
     - a `StackMapTable:` line.

   Keep them inside the existing method. A new test method would change `Ran 5`, `unit_tests:5`, the printed `units=5` and "Five units" in the doc, all of which assume five. Optionally, limit the scan to the lines between `public void store();` and the next method signature.

3. **Mutations that do several replacements aren't checked one replacement at a time.**
   - `text==source` (`:106`) only shows that at least one replacement happened. The exact-frame check catches a partial mutation indirectly, because it would fail at a different code.
   - `.replace('writer.flush();','writer.flush();')` at `:99` does nothing.
   - The `'        }\n    }'` replacement has no count check. I didn't read `PreferenceIO.java`.
   - *Fix:* assert `source.count(old)==1` for every pattern you replace, and delete the no-op replacement.

4. **Interrupt coverage only tests one direction.**
   - `clear-interrupt` clears the flag at entry, so only `interrupt-candidate-true` is proven to detect a cleared flag. Nothing shows that `interrupt-candidate-false` (flag set during serialization) can detect anything.
   - The ban on `java/lang/Thread` in the helper's javap check covers this structurally, so it doesn't block.
   - *Optional:* add a mutant that calls `Thread.interrupted()` after `writer.flush()`, and run it with the pre-set iteration disabled. If that's awkward, document that only one direction is tested.

5. **Some checks still use the generic `"general"` code.**
   - These are in `PreferenceWriteObservation.java:23, 36, 42, 56` (twice), `57, 76` (twice) and `78` (twice).
   - No negative control targets them, so the claim "case-specific codes" is true only for the assertions the controls target. Either say that in the doc or add codes.

6. **The candidate JAR hash isn't enforced.**
   - `candidate_sha` is recorded but never compared to `e0fe515d…` or to an expected-build value. The contents are pinned (`strip_entries(after)==before`, `PATCHED_SHA`, helper hash), but the ZIP container isn't.
   - *Fix:* compare it against a constant or the lock, so the hash quoted in the doc is actually checked.

7. **`class_major_version=47` is a literal** (`:123`). It's correct because `shape()` asserts it, but deriving it from `after[ENTRY][6:8]` would match how the other values are recorded.
