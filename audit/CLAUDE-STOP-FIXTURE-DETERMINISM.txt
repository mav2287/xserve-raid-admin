I found three blockers that will make the planned rerun fail or overstate what is checked. The fixture determinism fix itself looks correct. This was a read-only review: I didn't run anything or look at the git diff.

## Fixture builders (`tools/stop_admission_fixtures.py:22-26`, `tools/stop_exposure_fixtures.py:28-32`)

- **Timestamps:** every entry is written with an explicit `ZipInfo` dated `(1980,1,1,0,0,0)`, so the zipfile library never reads the clock. That fixes the original problem.
- **Order:** entries are written in `sorted()` name order, so the order of the input dict no longer matters. Each fixture is still checked after writing (non-Manager entries unchanged, hook reverses exactly).
- **Semantic changes worth recording:**
  - Every entry is now written stored (uncompressed) with new metadata, so the fixture no longer keeps the reference JAR's compression, timestamps, extra fields or entry order. Only entry contents are preserved.
  - Directory entries (names ending in `/`) get `0o100644`, a regular-file mode, and no MS-DOS directory flag. The JVM and Python both decide "directory" from the trailing `/`, so this is harmless. But "POSIX metadata" in the ledger shouldn't imply directory modes are kept.
  - In sorted order, any `META-INF/` file that sorts before `MANIFEST.MF` comes first. `-cp` loading uses `JarFile` and doesn't care. Only `JarInputStream` would.
  - Reading entries into a dict silently merges duplicate names. A one-line check that `len(namelist)==len(set(namelist))` would catch that.

## Test (`tests/test_stop_admission.py:40-55`)

- Patching `zipfile.time.localtime` is the right mock: it would catch a regression back to `writestr(str_name, …)`. With the current code the clock is never read, so the patch only matters as a regression guard. That's fine.
- **Gaps:**
  - The test only compares two runs in the same interpreter. It never pins a known hash, so a Python version that writes different ZIP headers would go unnoticed. Adding the expected SHA-256 of this tiny synthetic JAR would fix that.
  - The synthetic entries have no directory entry and no non-ASCII name.
  - It calls `write_fixture` directly, so it wouldn't notice if `build()` stopped using it. The assembler's exact hash comparison covers that end to end.

## Blockers for the planned rerun

1. **Test count is hard-coded at 136.** All three recorded runs say `Ran 136 tests`. If this test is new (likely; check the diff), the rerun prints 137. The assembler will then fail at `audit/stop-admission-evidence-assembler.py:104`, and lines 108 and 148 (`tests_passed`, `python_tests_passed`) would record the wrong number.
2. **The stop gate won't run in qualification mode with the untracked audit files present.** `tools/check_stop_admission_experiment.py:15,19` refuses any non-empty `git status --porcelain` unless `--development` is passed. The assembler also needs `fixture_dirty is False` (line 25). But the assembler requires the unit run's worktree status to match the assembly status exactly (line 102), so the unit run must have the archival files present. The order therefore has to be:
   1. Move the archival files out.
   2. Run the stop gate on a clean tree.
   3. Restore exactly the same archival set.
   4. Run the unit tests.
   5. Run the assembler.

   Any other untracked file, such as a saved copy of this review, fails line 21.
3. **The reference SHA isn't actually checked.** The expected hash for active legacy rows is `stop['application_reference_sha256']`, taken from the record itself (line 132). Nothing requires it to equal `9f3f…`. Line 110 checks the reference file on disk, not the record. `application_reference_source_commit` is also copied into the ledger without a check. Fix: require the hash to equal the audit21 constant, and compare the commit with `build/worker-exit-clean-3/provenance.json`.

## Checks that are weaker than described

- **Nested counts** are recorded (line 54) but never compared with expected values.
- **Factory identity:** line 69 only checks that the set of JAR hashes is {original, candidate}. A 3+1 split, or a missing architecture, would pass. Require the four (architecture, JAR) combinations exactly.
- **Stop coverage:** line 141 checks the 8 candidate + 8 reference active-control split correctly, and lines 119-120 count compiled and active rows. Nothing checks that all 104 (architecture, execution, scenario, policy) combinations are unique and complete; the worker gate gets such a check (line 64).
- **PASS checks** only cover `lines`/`results`/`result`. Other lists of strings, such as `recovery_regression`, only have their length checked.
- **Python pinning:** the assembler rebuilds the hook JARs without calling `verify_python()`, while the gate does. A different interpreter would fail rather than falsely pass, but calling it would make the two match.
