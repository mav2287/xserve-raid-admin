# Audit25 browser compatibility boundary

Status: implementation and development checks complete; clean qualification and release preparation pending. Hardware acceptance is deferred by the user. No controller contact is scheduled.

Facts: the original BrowserLauncher initializer dereferences absent `mrj.version` on both locked Corretto runtimes. Setting that property would select an existing no-op MRJ stub and create false success. The whole-JAR constant-pool inventory finds two external callers: RaidAdmin$HelpListener.actionPerformed and SystemMonitorController$UnsupportedOperationDialog.hyperlinkUpdate. HyperTextPane creates hyperlink events and delegates to listeners; it does not directly invoke BrowserLauncher. Exact-name reflection-string inventory includes only BrowserLauncher's own literal. Computed reflection is not exhaustively excluded.

The patch changes one two-byte invokestatic operand in each original class, appends three constants, and updates each pool count. Whole-class reversal recovers the pinned original SHA256. All other methods, fields, handlers, attributes and original pool bytes survive. The unchanged original BrowserLauncher library and unused references remain. Help uses the original Resources lookup; the support action still checks ACTIVATED and uses its original url field, rather than the event URL. All 18 bundles are retained; only base/de/fr/ja define these URL keys, with the other locales inheriting them. Original HTTP URLs are preserved without redirection or a claim that their content is available.

The Java8 helper calls Desktop.browse using an absolute URI without rewriting it. Null/blank, malformed/relative, unsupported browsing and native exceptions/linkage failures yield fixed codes without URLs, exception messages or stack traces. A fixed English modal error dialog is deliberate new failure feedback, with stderr fallback; it is not a claim of unchanged legacy failure behavior. Arbitrary absolute schemes passed by original API callers remain accepted; no new scheme policy is silently added. Fatal VM failures are not contained. No FileManager browser fallback or mrj.version spoofing is added.

Development checks: four 62-case ARM/x64 interpreter/requested-compilation runs, four interpreted missing-invocation mutants, an original-action browser-denial reachability control per run, and three explicit browser-permission guard controls per run. Each fixture refuses non-headless execution before doing work, denies browser permissions, sockets, processes, writes and profile reads, and verifies candidate/probe class identities. It tests actual Resources loading, both patched actions and the actual helper. The support dialog uses an Unsafe-allocated shell; its constructor, sheet presentation and controller actions are not exercised. Candidate actions are defined by the explicitly checked child loader. No actual Desktop.browse call occurs.

Excluded development failures: the first action fixture omitted the original Resources.load prerequisite; a scanner initially rejected BrowserLauncher's legitimate self-reflection literal; the first integrated checker collided its expected-build Path name with its expected output string. These were fixture/checker defects, corrected and rerun, not accepted passes. Transient syntax/path mistakes produced no qualified evidence. Standalone and dirty development records are distinct from future clean qualification. Claude reviews are static advice; reviewers read evolving source and sometimes an incomplete check directory. The completed records, independently checked hashes and clean reruns will be the execution evidence.

Audit25 JAR: `59087dceed5865b08cef4db0b554a0822837618a07e59b6fd92a2b25880e6393`. Removing only the seven hash-locked helper additions and reversing the two exact original UI overrides reconstructs every audit24 JAR entry. Controller commands, request serialization, polling, retry timing and transport bytes are unchanged. Network gates keep the actual candidate UI entries in their runtime/mutant artifacts; stripping is only an exact comparison operation.

Remaining unverified: native browser handoff, native error-dialog presentation, remote content, complete application startup/workflows, physical Intel, Developer ID/notarization/Gatekeeper and controller behavior. x64 execution is Rosetta. `-Duser.home` does not redirect the pinned runtime's FileManager preferences folder, so full Main must not be launched against the host's real saved profiles for an allegedly isolated test. Optional PasswordManager has no direct callers outside itself in the original constant-pool inventory; introducing a new Keychain feature is unsupported by that evidence. Public RaidSystem.paramString still contains credential fields; its conservative UI/program-logic consumer review remains a separate local security task. HTTP remains plaintext.
