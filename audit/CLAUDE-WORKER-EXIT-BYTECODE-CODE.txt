## Non-blocking notes

1. **Dormant requeue window, 380–459.** `addFirst(txn)` at 417 runs while `workerActiveTxn` still points to the same transaction. If an error escaped between there and 689, `exit` would build one entry from `active` and another from the queue for the same transaction, and both would get a callback. The queue identity check (lines 121–124) wouldn't catch this. The code is unreachable today: 349 and 583 branch to 563, and nothing targets 380 (`377 goto 459` only reaches the `goto 489`). Cheap insurance would be skipping `pending[i]==active` in `exit`, or making the normalizer assert that the region is unreachable.
2. **Worker-thread re-post after stop.** `postMessageAsync` 63–73 still adds to the queue when the caller is the worker thread. During `exit`, the synchronous SyncSender callbacks (line 131) run on the worker thread after `queue.clear()`. Anything they posted would be stranded. `SyncSender.handleResponse` presumably doesn't post, so the risk is low.
3. **`started` stays true after 667.** This is harmless, because `exit` ignores `started` when `active==null`.
4. **Exactly-once means per active slot, not per transaction.** The doConnect paths deliver a ConnectException with a null context in place of the transaction's context. This matches the predecessor's visible behaviour, because `retire` stops the manager, so 509 never fired after it anyway. The 401 path still has no null check on the handler; that was already the case before this patch, and an NPE there is caught by the 462 handler.
