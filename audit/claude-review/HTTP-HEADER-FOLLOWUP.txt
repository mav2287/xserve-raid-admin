## Checked against the original bytecode (`build/http-response-allocation-bytecode.txt`)

- **`readLine` (lines 236–274):** a non-ending byte doesn't reset the newline flag (59–64). The second CR or LF returns (46–51). `-1` returns whatever has been collected (18–31). `BoundedHeaderStream.java:20-33` does the same.
- **`parseHeaders` (157–234):** an empty status line throws `EOFException`. An empty header line returns. An `indexOf(':')` of 0 or less throws `ProtocolException`. `finish()` matches this: it switches to body mode only when `lines>0 && characters==0`.
- **Constructor (14–38):** the stream is stored with `putfield` at 36, there's no exception table, and the only branch (10 → 23) lands before the insertion point. So the 3-byte shift can't move any branch target, and the "earlier branch unchanged" claim holds.
- **Limits:** you can't reach unbounded bytes or lines without non-ending bytes. A blank line after the status line switches to body mode, and a blank status line fails, so `lines` stays at 130 or fewer.

## Corpus blind spot: fixed (source observation)

At every corpus case, `HeaderObservation.java:38-48` checks the final wrapper state against two oracles. One runs the real `parseHeaders` on a wrapped shell. The other calls the real `readLine` on an unwrapped shell, with test code supplying the loop.

- If the wrapper switched to body mode too early, it would stop counting, so `bytes` would fall below `consumed`. A rejected case would also end with `body=true`.
- If it switched too late, an accepted case would end with `body=false`.
- The line count and the reset fields are compared as well.

That covers the defect I raised before. The test's loop at `:46` rewrites the loop logic of `parseHeaders`, but `legacy.consumed()==consumed` checks it against the real one. The line count is 1 corpus + 4 accepted + 1 fresh-response + 1 PASS = 7, plus 3 rejections = 10, which matches `check_architectures.py:125`.
