# Design review: shared persistent stream characterization

## Verdict
The main claim holds up against the bytecode, but only if the fixture fixes the problems below. When the first response is missing its length (or declares 0, uses a lowercase header, or has a duplicate last-zero length), the parser leaves that response's body in the stream. With the connection kept open, the next `HttpResponse` parses those leftover bytes as if they were the reply to the second request. Three of the issues (1–3) could make the result an artifact of the fixture rather than of the app.

## Confirmed by the scoped bytecode
- **One stream fetch per response.** The `HttpResponse` constructor calls `connection.getInputStream()` exactly once (`http-response-allocation-bytecode.txt:34`). `AcpxConnection.send` calls `getResponse()` once (`acpx-response-callers-bytecode.txt:153`). The existing override would already fail with "Response before request" on a second call (`TransportObservation.java:53-55`). So the design's worry about repeated `getInputStream` calls doesn't apply to the original code. Still, make the fixture assert one `getOutputStream` and one `getInputStream` per request: the override replaces `pending` on every `getOutputStream` call (`TransportObservation.java:50`).
- **The parser never closes the stream on a normal persistent reply.** `getBody` only closes the stream if the connection is not persistent or the response said `Connection: close` (`http-response-allocation-bytecode.txt:122-130`). Persistent mode is on in the existing setup (`TransportObservation.java:48, 84`), and `addHeaders` leaves out `Connection: close` when persistent (`acpx-response-callers-bytecode.txt:317-325`).
- **Missing or zero length leaves the body unread.** With length 0 nothing is read (`:59-81`). The empty body means `available()==0`, so `send` returns null, which the fixture reports as "empty". `requestOutstanding` is cleared at `:183-188`, so the second `newRequest` is allowed.
- **Duplicate headers: the last one wins.** `parseHeaders` calls `setHeaderField` once per line (`:207`), which matches the existing outcomes.

## Issues to fix before implementing
1. **`disconnect()` must not be a silent no-op.** In the real code, `disconnect` sets the socket to null and `connected` to false (`http-connection-bytecode.txt:135-160`). Reconnecting creates a new socket, which throws away any leftover bytes. If the shared source survives a disconnect, you'd see contamination the real app can't produce. Make `disconnect` record the event and make the source unusable afterward. Also assert that `acp.connection` is the same memory instance after send 1. If it were null, `send` would call `createConnection` and build a real `HttpConnection` (`acpx-response-callers-bytecode.txt:80-84, 274-293`). OfflineGuard would catch that, but as a failure, not as a measured result. This also matters for audit.10: its rejection path sets `acp.connection` to null (`TransportObservation.java:119`).
2. **What happens when the source runs out must be stated.** `readLine` treats end of stream as the end of the line and returns whatever it has (`http-response-allocation-bytecode.txt:18-31`). An empty header line silently ends header parsing. So a read that returns -1 can make a short or drained source look like an "empty" success. An open socket would block or time out instead. Use the existing idle-timeout pattern (`TransportObservation.java:66`), throw it whenever reads go past the scripted bytes, and say so in the report.
3. **`close()` must be terminal, not just counted.** If a response says `Connection: close`, the parser closes the stream (`:122-130`). On a real socket that closes the socket, but `HttpConnection.connected` stays true. Make reads after close throw, or a `Connection: close` variant will overstate how persistent the connection is.
4. **The line framing is unusual, so pin it to CRLF.** `readLine` ends a line on the second CR/LF byte, and the flag is never reset by ordinary characters (`:34-66`). So `\n\n` counts as one terminator, and a lone LF does not end a header. The forged and legitimate replies must use exact CRLF, or results will depend on framing quirks. That should be a separate characterization, not mixed into this one.
5. **Check audit.10 rather than assuming it matches.** The current build routes body reads through `compat.BoundedResponseBuffer`. If audit.10 buffers or reads ahead on the input, leftover bytes could be swallowed and the outcomes would differ. Assert the source's remaining-byte counts on both builds, not just the parsed results. I couldn't check this, because the audit.10 source is outside the scoped files.
6. **Prove where the forged bytes came from.** To show they're leftover body and not a reply you preloaded:
   - Immediately before the second `getInputStream` appends anything, remaining bytes must equal the forged reply's length exactly.
   - After the second parse, remaining bytes must equal the legitimate reply's length.
   - Before the first fetch, remaining must be 0.
   - Give the forged and legitimate replies different plist values, and compare the plist root, not the typed `getTime` response. A status-shaped plist parsed as a time response could fail or return a code for unrelated reasons.
7. **Error messages contain raw peer bytes.** `ProtocolException` includes the bad header line verbatim (`:141-147`). The fixture must report exception types only, never messages. Leftover bytes from a misframed reply could end up in that message.
8. **Two pieces of the code path weren't in scope.** I couldn't see `HttpResponse$HttpInputStream.close()`, which uses the `access$000` accessor for the connection (`:292-296`) and is closed in `send`'s finally block (`acpx-response-callers-bytecode.txt:328-335`). I also couldn't see `HttpRequest` (when `requestSent` gets set) or how `HttpMessage.getHeaderField` handles case. If `HttpInputStream.close()` disconnects or closes the socket, the whole premise of a shared stream changes. Read those, or record a stream close count of 0 as a required check that fails loudly.
9. **The memory bounds contradict each other.** The doc says "bounded 64MiB", "≤8192 per script" and "reads ≤16384" in different places. Pick one per-source read cap and one heap flag. Also require any `Content-Length` inside the forged reply to be small and exact, so the original code never allocates a large buffer.

## Suggested additional case
A plain chunked response is a likely way for an honest server to cause this desync. The existing "chunked" case returns "empty" (`TransportObservation.java:145`), but on a shared stream the leftover `3\r\nabc...` would be read as the next start line, and `abc` as a header with no colon, which raises `ProtocolException`. That would show the same leftover-byte problem occurring without a forged reply.

## Wording limits for the report
- Describe the result as **response association on a shared stream inside this parser**.
- The fixture does not prove anything about TCP. It has no segmentation or real timing, and the peer answers instantly on request capture.
- It does not show controller behavior, backoff, or reconnection.
- It is not an authentication bypass. `ACP-User` and `ACP-Password` still go out in plaintext, and a peer who can inject these bytes could already forge a direct reply to request 2. The extra risk is mostly accidental desync (chunked responses, honest peers with unusual framing) and misattributed results, not a new attacker capability.
- Stricter header parsing on the client can't authenticate the peer or encrypt plain HTTP, as the design already notes.
