## Concurrency and lifecycle: correct

- **Nothing is left in the queue on a normal stop.** The worker's exit check (run PC34–53) reads `size==0 && stopped` under the queue lock, so a post admitted under that lock is either drained or sees `stopped=true`.
- **Worker exemption is safe.** The worker always goes back to PC7 after a callback. SyncSender's own same-thread guard rules out synchronous posts from the worker.
- **SyncSender direct path is safe.** The post happens before the sender's monitor region, at constructor PC14–19 (handlers start at 24). `handled` is set before the check, so `wait()` is never reached.
- **No new lock-order risk.** The helper runs after `monitorexit`. `invokeLater` doesn't block, so callers that hold a lock, such as the synchronized `RaidSystemAgent.connect`, are fine.

## Non-blockers (with fixes)

1. **Code-length pass-through is too loose** (`class_patch.py:567`). `if u4(data,b+10)==56: return data` skips every check based only on the code-length field. Today every caller re-checks a hash afterwards, so nothing gets through, but that's fragile. Fix: `if data[b:e]==POST_CODE: return data`. This is exact for original/audit17/18/19, since that method and CP≤394 never changed.
2. **The sync test can't tell the direct path from the EDT path** (`StoppedPostObservation.java:55`). If `instanceof` always gave false, the SyncSender would be notified from the EDT and the test would still pass. Byte pins cover this, but the behaviour test gives a false positive. Fix: in fixed sync mode, after `join`, assert that no `AWT-EventQueue` thread exists, the same check `nullAndClone` uses.
3. **The concurrency test can miss a late duplicate** (`:72`). A 33rd duplicate event could still be waiting on the EDT when the counts are read. Fix: call `SwingUtilities.invokeAndWait(()->{})` before the final check.
4. **The containment boundary is untested.**
   - Nothing shows that a non-Linkage `Error` thrown by a handler reaches the EDT uncaught handler without the fixed log being written.
   - Nothing shows that an appender throwing a `RuntimeException` inside `signal()` is contained.
   - Add one mode covering both. Also record that `LinkageError` from a handler is contained (the RejectionRecovery idiom), so "fatal errors propagate" means non-Linkage Errors only.
5. **The security gate doesn't require the admission** (`check_security.py:110`). It calls `normalize_admission(..., required=False)`, so a Manager without the admission still passes there. `check_stopped_post` passes `True`, and `expected-build.json` pins the build identity, so the risk is small. Consider `required=True` when the field is volatile and CP395+ exists.
