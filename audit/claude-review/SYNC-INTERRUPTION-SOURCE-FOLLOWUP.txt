## Firmware `UpdateThread.run` (:3151–3184)
- Each cache disable and re-enable has its own `catch Exception`. A failed re-enable sets `access$1702(true)`.
- **Re-enable only runs when the flash succeeds.** A non-zero flash status returns through the finally block (`jsr 1704; return` at 283–286). An IOException or PropertyListException from the flash goes to 1622 or 1650, then the finally. Both paths skip the re-enables.
- The finally block (1704–1759) runs `clear`, `authenticate(...)` and `setPollingEnabled(true)`. It never re-enables caches.
- So caches can stay disabled after any flash failure **today**, regardless of interrupts. Point 4 in the design should say M adds a session shutdown that also breaks the finally's `authenticate` post.
- Every sleep and poll catches and swallows InterruptedException, so no interrupt status survives in this thread. Nothing in scope interrupts it.

## New semantic issue: connect-failure callback before the claim
`doConnect` calls the handler's `handleResponse` with a -101 ConnectException *before* the claim. That happens at 401–414 (no valid address, then return) and 578–596 (connect failure, then it keeps retrying until connected or stopped). For a sync caller this sets `handled`, so `postMessage` throws ConnectException.

- **Today:** after a later reconnect, `run` still sends the orphaned request. In the no-valid-address case it calls `send` on a null or stale connection; a null one throws NPE → 462 → `report` stops the session.
- **With the claim:** it's refused because `handled` is set, so no send and no stop.
- That's an improvement, but it's a behaviour change. In the sync no-address case the session is no longer torn down, and the next post retries `doConnect`. Async handlers are unaffected (the `instanceof` check).
- **You need to accept this explicitly.**

## Behaviour of the narrow milestone (no bounds claimed)
- **Before the claim**, whether queued or anywhere inside `doConnect` including its backoff sleeps: the interrupt cancels, the caller gets an IOException, and the session is untouched. No bytes of this request were sent by this client.
- **After the claim**, the caller waits for the worker's real answer. That window covers a possible unbounded connect, unbounded writes, a 30 s-per-read default with an unlimited number of reads (infinite in the SO_TIMEOUT edge case), cleanup and the callback. **The app doesn't bound it, and neither does this design.**

## Residuals
- If the worker dies after the claim (an Error, or `report`'s "stop failed" exception at 464–467, which has no handler), the interrupted caller hangs.
- A sync post from inside a handler callback (constructor 31–50) throws after it was already enqueued. The worker later claims and sends it.
- The `isStopped` check at 234 runs before the claim, so a shutdown that lands between them still lets the send go ahead.
- Interrupters outside the inventoried code are still unknown, and so are the GUI caller threads (inventory lines 14763, 14808, 15340, 26936).
- The `UpdateFirmwareRequest` timeout isn't visible because its constructor isn't extracted. Any value of 0 still becomes 30000.
