## Precision fixes to make in the same commit

- **`queued_restart=sent` depends on the fixture's own setup.** The fixture clears `requestOutstanding` itself (`TransportObservation.java:82`).
  - For a real prefix failure that happens after the whole body has been read, that matches how the original behaves: the response stream's close clears the flag.
  - For shim or generic failures thrown partway through a response, the flag may stay set. The next `newRequest` would then throw `IllegalStateException` before writing anything (`REJECTION-RECOVERY-FOLLOWUP-DESIGN.txt:27`). In that case the restart gets -102 without being sent, and the session still does not stop.
  - The doc should keep these apart: "not stopped" holds whether or not the flag is cleared, while "restart sent" holds only when the connection is reusable.
  - Findings line 15–16 ("can process queued writes") should say this. The `operation_failure_scope` wording ("…not all failures and queued synthetic restart…") is garbled and should be rewritten.
- **The labels for the getPath fault disagree.**
  - The `--operation-failure-characterization` help text (`check_transport.py:114`) and the refinement doc §5 both say "pre-serialization".
  - The fixture and the scope string say "before-request-creation".
  - Use "before-request-creation" everywhere, and add that the fault comes from a proxy seam, not from a throw site in real code.
- **The shim claim** (findings line 51–52) should say "the shim class's only constant-pool reference is in Manager, and `run`'s catch table uses it". A constant-pool scan doesn't show which instructions in Manager use the class.
- `operation_failure_scope` is written out even when the flag is off. The other `*_limits` fields use `None` in that case.
- The identities JSON says "All2844"; it needs a space.

## Gate assessment

- The exact-line Python gate is solid. It rejects truncated, duplicated, prefixed and wrong-mode output, and its error text never contains the raw output. However:
  - **The unit test is circular.** `OperationFailureGateTests` builds its expected lines with the same formula as `completed_operation_failures`. Add the literal four original-mode lines from the artifact as a golden copy.
  - **The stop mode is detected from the jar, not required by a flag.** The tool searches the class bytes for `STOPS_OPERATION_FAILURES`; the fixture reads the field's value. If the two disagree, the gate fails closed, which is good. But a candidate without the marker silently runs as a characterization. That's fine for this commit. The worker-stop patch needs a required `--operation-failure-policy` flag that must match the jar, like the terminal-I/O check at `:166-167`.
- **The stop-mode branch has never run** (`TransportObservation.java:469-470`); no jar has the marker yet. Either label it as such in the commit message or doc, or hold it back until the patch.
