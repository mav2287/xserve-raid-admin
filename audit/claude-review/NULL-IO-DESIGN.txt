## Verifier (class version 47 uses the old type-inference verifier, which needs no stack-map frames)

- **Merge at 344:** it is now reached only from 573. The stack there is `[String]`, the same as at the original 344, and locals 0–5 match the IOException handler's state (local 5 is IOException).
- **Merge at 464:** it is reached from the 462 fallthrough (stack empty, local 5 = Exception) and from 568 (stack empty, local 5 = Exception from the `()Ljava/lang/Exception;` return). Both match. The already-patched `report(CommunicationsManager, Exception)`, the `BasicResponse` constructor at 474 (`…ILjava/lang/Exception;`) and the 489 callback all accept that.
- **Exception table:** 339 sits inside `0–522 InterruptedException`. The handler at 525 only runs `astore_1`, so the new local-5 types don't matter to it. The appended block lies outside every range. That matches the original, where handler code was never protected either.
- **One evaluation of `getMessage`:** `dup` means `getMessage()` runs exactly once, as in the original. That matters for subclasses that override it. A design that re-called it would have an unsafe check-then-use gap.

## Security semantics

- **Null message:** the request fails terminally with −102, one callback, no requeue, and the connection is retired through the existing exact-class branch in `report`. Previously the worker died, so this replaces worker death and does not remove a replay that used to happen. It's conservative, and "outcome is unconfirmed" is accurate whether the failure happened before or after the send.
- **Dropping the cause is the right call.** A null-message IOException can still carry a cause whose message contains peer text (for example a wrapped `ProtocolException`), and `log(failure, failure)` would print that chain.
- **Unchanged behaviour:** non-null messages still reach 344 with the same String, so the −103 prefix path, the requeue/doConnect path and their timing don't change.
- **Reusing `UntrustedResponseException` stretches its "untrusted response" meaning**, but it's the only exact-class key `report` retires on. Its constructor is package-private, so `nullMessage` has to live in `compat`, and `RejectionRecovery` does. Update its javadoc so it no longer says only response guards construct it.
- **Side effect:** if a peer causes null IO every time, every request (including polls) gets −102 and a reconnect. Load is bounded by the request rate and nothing is replayed, but the GUI will show repeated −102s.
- **What the fix doesn't cover:** if `nullMessage()` itself fails (OOM or LinkageError), or an overridden `getMessage()` throws, the worker still dies, exactly as before. Say so in the limits.

## Tests to add beyond your list

- **`getMessage` call order:** an IOException subclass returning null then `"x"` must go terminal; one returning `"x"` then null must requeue without an NPE. This shows `getMessage` runs once.
- **Cause chain:** `new IOException()` with a cause containing a peer-text marker. The callback's exception has no cause and the fixed message, and the captured logs don't contain the marker.
- **`EOFException()`:** the most likely real source of a null message from the JDK.
- **Unchanged paths:** the existing truncated-retry, drops=1/4 and malformed (−103) vectors produce the same output.
- **Sync caller:** gets an IOException with exactly the fixed message and no cause, within a time bound.

## Alternatives considered

- **3-byte in-place swap:** replace `invokevirtual #71` with `invokestatic message(IOException)String`. The smallest possible edit, but a null message then has to go down either the requeue path (replays a possibly-applied mutation) or the −103 path (labels it a parse error, never retires the connection, and leaves the stream possibly out of sync). Reject.
- **NPE catch row over 339–349:** catches more than intended, and the handler would still need the same retirement routing. Reject.
- **Your null-check-and-branch design is the smallest correct option.**
