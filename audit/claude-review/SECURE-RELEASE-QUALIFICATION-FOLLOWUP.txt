## 1. Stop-lock "output differs" failure

**What the failure tells you (`audit_support.py:69-81`, `check_stop_lock.py:76-77`)**
- `run_jdk` raises `RuntimeError` on a nonzero exit, and `subprocess.TimeoutExpired` on a timeout. Neither one would reach line 77. So both canonical failures had **exit 0 with stdout that wasn't the expected two lines**.
- `StopLockObservation` only prints after every `check(...)` passes, and any failed assertion gives a nonzero exit. So the fixture's own oracle passed. Your whitelist diagnostic agrees: the two correct lines were there, plus something extra.
- Nothing in the fixture writes anything else to stdout. Uncaught exceptions in daemon threads go to stderr, and log4j `LogLog` warnings also go to stderr. `LogLog.debug` would go to stdout, but your config review says `log4j.debug` isn't set. Writes the guard blocks raise exceptions rather than producing output.

**Most likely source: the JVM printing to stdout.** In JDK 8 HotSpot, `warning()` and similar messages go to stdout by default (`-XX:-DisplayVMOutputToStderr`). On macOS these show up intermittently as `... VM warning: Attempt to protect/deallocate stack guard pages failed`, more often under Rosetta x64. `pc18-getter-restored`/`pc18` is the **first deadlock vector** in the sequence (`check_stop_lock.py:79-82`). It is the first run where the JVM exits with two daemon threads stuck on monitors. That makes it a plausible spot for exit-time VM chatter, but I can't confirm this without seeing the bytes. A SIGQUIT thread dump from an external sampler would also go to stdout.

**Visibility gaps that hid the cause**
- `run_jdk` drops stderr completely here (`require_empty_stderr=False`), so a matching stderr signal would be invisible.
- The line 77 error doesn't name the architecture, execution mode or label, and a failing vector leaves no observation behind.

**Diagnostics to add without weakening the oracle.** Keep line 77's exact `splitlines()==expected` comparison as the only pass condition, and keep the content-withheld policy. Only on a mismatch:
- Raise with the controlled labels (`arch`, `execution`, `label`, `mode`) and record the return code.
- For both stdout and stderr, record the byte length, SHA-256 and line count, plus the positions of the expected lines.
- Sort each extra line into fixed buckets using anchored regexes, e.g. `^(Java HotSpot\(TM\)|OpenJDK) 64-Bit \w+ VM warning: `, `^log4j:`, `^Full thread dump`, `^Exception in thread`, or other. Record the bucket and a hash, not the text.
- Optionally write the raw bytes to a new 0600 file under `build/`, marked non-evidence.

**Changes to avoid**
- Don't add `-XX:+DisplayVMOutputToStderr` to the qualifying argv. `run_jdk` ignores stderr, so VM warnings would just disappear. That's a weakening, and it changes the frozen argv. Use it only in a separate diagnostic run, and only together with full stderr classification.
