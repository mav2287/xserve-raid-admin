## Gate precision (should fix before calling this clean)
- **`assert_retry_unreachable` has no positive reachability check** (`check_security.py:36`). Make it assert that the unreachable set is exactly the instructions in 380..458, and that 231, 6/28/60, 352..377 and 534..545 are reached. Today only byte equality protects these; the reachability walk run on the `.javap` fixture would accept a mutant that cut them off.
- **The `ifeq` literal check at line 18 decides most "CFG" tests, not the walk.** All 6 wrong-target tests in `test_terminal_io_gate.py:14` fail on that literal check, so only the handler-retarget test and the `goto 459→380` test actually exercise the walk.
- **The semantic negative accepts any `AssertionError`** (`TransportObservation.java:344`). A mutant that broke for an unrelated reason would still count as "fails containment". Match the specific failure: a non-marker exception, or stopped=false with a second send.
- **Result codes are checked, but continued dispatch is not.** Only -103 asserts `!isStopped()` before the callback (`:267`). ACP -16/-27/-28 and `http-*` (`:285-288`) check only the result code. "Queued valid-controller result codes preserved" holds for the codes; that these results don't stop the session is asserted only for -103.
- **The `complete_requests` label overstates what was measured.**
  - It means the request was written and `getInputStream` was reached, not that a response completed.
  - response-loss/empty/timeout/EOF are all thrown when `getInputStream` is entered (`:76`).
  - Mid-header EOF/timeout and a real shared-stream idle close aren't modelled; idle-close is EOF injected on a fresh stream.
- **Close-once isn't asserted for the terminal faults.** cleanup-after-reply checks only that `closeFailures==0`.
- **`-Xint`/`-Xcomp` cover only the terminal fault matrix.** -103, dispatch/queue and both negatives run in default mode only. Under `-Xcomp`, the 2 s `join` (`:419`) may time out; that fails closed, but it could make qualification flaky.
