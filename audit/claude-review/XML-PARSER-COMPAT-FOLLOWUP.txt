## Remaining issues

**1. Entity expansion is still large (design gap; not demonstrated, nothing tests it).** `SafePlistParser.java:18` keeps the JDK defaults of `entityExpansionLimit=64000` and `totalEntitySizeLimit=50000000`. A document of roughly 2–3 KB can stay under both limits and still expand to about 50 million characters, around 100 MB of Java memory before buffer growth. It would use one 782-character entity, a second entity referencing it 250 times, and about 254 references to that second entity.
- This is far tighter than the original's bundled Xerces, which has no limits at all.
- Given your priority on security, the 64000 / 50M values are inherited defaults, not something compatibility needs. The original-vs-candidate cases need at most about 3.6k characters of entity output.
- `totalEntitySizeLimit` is never tested, and the limits text admits the size controls don't separate total from per-entity size.
- I'd recommend lowering `totalEntitySizeLimit` (and probably `entityExpansionLimit`) to a bound based on the largest realistic controller reply. The 63,900 and 70,000 cases in `ParserPolicyProbe` would need adjusting to match.

**2. Realistic document headers are not tested (unqualified path).** Every original-vs-candidate fixture starts directly with `<!DOCTYPE plist SYSTEM …>`.
- None has an `<?xml … encoding="…"?>` declaration, a BOM, a non-UTF-8 encoding, or the usual `PUBLIC "-//Apple Computer//DTD PLIST 1.0//EN"` form.
- Swapping the provider changes encoding detection, and the resolver may match on the PUBLIC id.
- Real plists usually have both, so this is the most realistic input shape the parser comparison misses. Other probes may cover it, but these files don't.

**3. Depth is tested with single-chain nesting only (unqualified path).** There are no sibling containers or multi-key dicts near depth 30. If the Handler's stack index can drift from the actual element depth, the candidate would inherit the legacy array-bounds failure. That would still match the original's behaviour, so it's low risk.

**4. Minor gaps in the evidence**
- The `limits` text in `check_xml_resources.py:106` doesn't mention the dict/mixed/empty 30/31 comparison.
- `check_architectures.py` hashes its fixture sources only at the end, without checking they were unchanged from the start. It also never compares parser output across runtimes.
- The Java 11 run covers accepted-value parity only. The quota, depth and hostile-flag probes run only on the pinned 8.504 runtimes, so the claim "Java 11 exercised" should be narrowed to accepted values.
- Matching on `"64000"` is a little loose. Matching the `JAXP00010001` message code would be exact.

Disposition: The remaining entity-size concern is accepted. Limits tightened to explicit 1 MiB total custom entity size, 256 KiB per general entity / 64 KiB per parameter entity, 4096 expansions and 100000 replacements. Independent positive/rejection probes added for total size and general entity size, and entity-count diagnostics match JAXP00010001. These bounds intentionally restrict unsafe legacy input; real-controller compatibility is unresolved. Default measurements remain evidence only, not the application policy.
