**Verdict:** I found one blocker, and it is in the evidence, not the patch. I found no bugs in the bytecode or the tooling. This was a read-only review: I ran nothing and recomputed no hashes.

## Blocker

**`waited=true` is printed but never checked** (`TransportObservation.java:754-758`). The caller is treated as waiting once the poll loop sees `q.size()==1` and `caller.isAlive()`. That only proves the request was queued. When `worker.start()` runs, the caller could still be anywhere between PC129–134 and `wait()`: running the enqueue, taking the trampoline `goto 20`, or blocked on the monitor at PC23. If so, the worker's `handleResponse` sets `handled` first and the caller skips the wait. The fixture still passes and still prints `waited=true`. This matters because the off-worker path through the trampoline into the wait is the main thing the candidate changes for healthy callers.

The fix is to poll until `caller.getState()==Thread.State.WAITING` before `worker.start()`, with the same 5 s limit. The only `wait` reachable in `postMessage` is the SyncSender monitor wait, and the queue lock shows as BLOCKED, not WAITING. Otherwise, rename the line to `queued=true`. Either change alters `TransportObservation.java`, so its source hash in the posting record changes too.
