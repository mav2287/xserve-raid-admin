**Order of operations (fact).**

## Findings

1. **The main failure path never checks "stopped before callback" from inside the callback (test gap; fix before qualification).** `ConnectFailureObservation.java:58` reads `isStopped()` only after `caller.join`. A mutant that ran the callback first and `retire` second would usually still pass, because the worker retires right after waking the caller. Only the no-host path asserts this from inside the callback (`:78`). The two mutants at `check_connect_stop.py:78` only remove the stop; they never reorder it. The order is pinned statically, so the candidate itself is safe; the problem is that the runtime evidence is weaker than the claim.
   - Fix: add single and dual modes with an async handler that asserts `isStopped() && !isConnected()` and that a synchronous post is rejected, all inside `TYPE_CONNECT`.
   - Also add a callback-then-retire mutant.

2. **I couldn't verify the audit.17 pin.** `AUDIT17_MANAGER_SHA256` at `class_patch.py:22` appears nowhere else in the repo. The ledger (`audit/sync-preenqueue-final-integrity.json`) records only a jar hash, so I can't confirm that "audit.17 with the original doConnect restored" really equals the audit.17 class. The method itself is sound, because audit.18 adds no constant-pool entries. Record the derivation, for example `sha256(CM)` taken from the ledger's audit.17 jar, and check it in `check_connect_stop.py`.

3. **A synchronous post can now hang forever after an initial connection failure (inference; new exposure).**
   - `postMessage` checks `isStopped` (pc 0) before `SyncSender` enqueues. `SyncSender.<init>` then waits with an untimed `wait()` and never checks whether the manager stopped (`tests/fixtures/sync-preenqueue-candidate.javap:116-127`).
   - If the worker leaves its loop (run 34–53) between those two steps, the caller blocks forever.
   - Before audit.18, initial failures never stopped the worker, so this window didn't exist on that path.
   - The limits text at `check_connect_stop.py:102` mentions only late async posts stranding. Disclose the sync case, or add a stopped check plus notify inside `SyncSender`'s wait loop.

4. **Smaller points:**
   - If the reported-path callback throws, line 594 is skipped, so the handler gets a second -102 from run 462→489. It's harmless for `SyncSender` but untested; `nohost-throw` covers only the no-host path.
   - The `-Xcomp` dual-host run allows `caller.join(15000)` against a random 5–10 s backoff. A slow x64 runtime could produce flaky failures. These fail safe.
   - The semantic mutants run only under `-Xint` and only in single-host mode for the reported path. There's no dual-host mutant.
   - The `scope` field in `audit/connect-stop-recovery-expected.json` says "Audit.17", but `check_connect_stop.py:42` uses its hash as the audit.18 candidate. Relabel it.
   - Behaviour change: after an initial connection failure the manager is now permanently stopped, so GUI reconnect depends on the app creating a new manager. The limits already say this is unqualified; make sure that's accepted product behaviour.
