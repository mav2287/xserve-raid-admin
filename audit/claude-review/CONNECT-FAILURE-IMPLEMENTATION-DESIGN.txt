## 3. Fixture corrections

1. **The dual-host candidate does sleep.** The first failure is silent (`lload3==1`, so `ifle 599` is taken), then 5–10 s of backoff, then the second constructor call publishes and W2 stops. Expected: 2 constructor calls (P, then S), 1 sleep, 0 sends.
   - The original dual-host run makes 3 constructor calls with 2 sleeps. Backoff is `x*3/2+1`, so the total is **12.5–25 s**.
   - The original single-host run sleeps 5–10 s. The single-host candidate doesn't sleep at all (599 → 606 → 692).
2. **The 35 s budget only works with one sleeping scenario per process.** Original single + original dual + candidate dual + null handler adds up to more than 35 s.
3. **An in-process watchdog cannot work.** `OfflineGuard.checkExit` denies all exits, and `Runtime.halt` also calls `checkExit`. The timeout has to be enforced by the parent runner.
   - Never interrupt the worker. That diverts it to 684 → 692 (and `SyncSender` to −102), which changes the path under test.
4. **`OfflineGuard` does not block all file access.** It blocks writes, deletes, exec, exit, sockets (including resolution via `checkConnect`), Preferences, and reads under `/Library/Preferences` or the sentinel path. Other reads are allowed, and class loading needs that. Describe it that way.
5. **The sync exception is a new object.** The original code builds `new ConnectException(ioe.getMessage())` at 549, so it is never the stub's exception object. Assert:
   - exact class `java.net.ConnectException`
   - the stub's synthetic message
   - `getCause()==null`
   - not the same object as the stub's exception

   Identity holds only between `response.getException()` and the object `postMessage` throws (PC59–72), which only an async recording handler can observe. On the no-host path the message includes `getName()`, so the fake name must be synthetic.
6. **No-host case, per runtime:**

   | Runtime | Callbacks | Manager | Other |
   |---|---|---|---|
   | Original | 1 (−101) | not stopped | NPE at `run` 255 escapes `run`; there is no generic row |
   | audit.17 | 2 (−101, −102) | stopped | — |
   | audit.18 | 1 (−101) | stopped before the callback | flag suppresses 273; later queued items get −102 each |

   - **Null handler, audit.18:** the flag is set and the manager stops, then the NPE at 409 goes to `report` and on to 489, where the null handler is skipped. Result: 0 callbacks, stopped.
7. **Throwing callback, audit.18:** 2 callbacks. `report` → 474 builds a −102 without checking the flag. The second throw at 509 escapes `run`, so 534 `close` is skipped and the queue is stranded. An `Error` escapes immediately, with the manager already stopped.
8. **Close count is 0** for a fresh manager. `connection` is still null because the constructor threw before `putfield` 424, so `retire` closes nothing and neither does 534.
9. **Null handler in the retry path is unchanged in both runtimes.** It retries silently and sends after the later success. That is the qualified limitation, and it needs its own process because it sleeps 5–10 s.
10. **Original-runtime shutdown must happen on the worker thread**, for example from the stub's `send` hook or a success callback. The lock inversion (`run` 7–53 holds the queue lock and calls the synchronized `isStopped`) can hang a `shutdown()` called from the main thread.
11. **The polling −101 case from the GUI-recovery review can't happen in audit.17 or audit.18.** Every exception in `run` 215–304 now stops the manager:
    - `349 ifeq` goes to 563, so 380–458 (including the 454 `doConnect`) are dead.
    - The MalformedInputException row was rerouted to 462.

    A live manager therefore enters `doConnect` only before its first successful connect. **This revises C1:** an outage on an established session is already terminal since audit.16, and it reports −102, not −101. B's added availability cost is limited to the first connect of each RaidSystem (launch or Add). Keep the polling scenario as an original-only control, or drop it.

## 4. Classpath stub vs child-first loader

**A normal classpath stub is enough** if every condition below holds:
- **Separate JVMs.** Each runtime, and anything sharing the real `AcpxConnection`, runs in its own process. Recovery and Transport observations break if they share the stub's classpath.
- **Order.** The stub directory comes before the candidate jar, and it contains only `AcpxConnection`.
- **Same shape as the real class** (javap header: superclass Object, no interfaces):
  - `public class` with public `<init>(String)`, `getHostAddress`, `send`, `close` and `disconnect`
  - `RejectionRecovery` in `compat` calls `close()`, so `close()` must be public
- **Provenance assertions.** Check that:
  - `AcpxConnection`'s CodeSource is the stub directory
  - `CommunicationsManager` comes from the candidate jar, with a SHA match on its resource bytes
  - `compat.RejectionRecovery` comes from the expected location

**Why this is likely safe:** `RecoveryObservation` already sits in `com.apple.xsr.net`, loads from a separate classpath entry, and writes package-private jar fields (`a.host`, `a.connection`). A sealed or signed package would reject it. That is an inference from those fixtures passing.

**When a child-first loader would be needed:** only to hold both the real and stub `AcpxConnection`, or both the original and candidate manager, in one JVM.

**Accepted cost:** the stub shadows audit.17's patched `send`, so the transport gates must still qualify it separately. Record sends by request identity, not bytes. Byte parity stays with `TransportObservation`.
