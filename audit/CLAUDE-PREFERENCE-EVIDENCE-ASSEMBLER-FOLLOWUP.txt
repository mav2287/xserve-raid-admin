## Proof the files contain but the draft never binds (suggestions, not blockers)

1. **Runtime trees.** Both files record the same `runtime_trees` (aarch64 ce517f…, x64 6aa1fb…). The final record writes `fixture_runtime_trees` from `runtime_lock` but never compares them. Add:
   `require(preference['runtime_trees']==model['runtime_trees']=={a:runtime_lock['architectures'][a]['tree_sha256'] for a in ('aarch64','x64')})`
   This is the most worthwhile addition: as written, the record states runtime trees it hasn't checked against the fixtures.
2. **Negative-control jar hashes.** Nothing checks that a negative ran a mutated jar rather than PIN or REFERENCE. Suggested checks:
   - Preference: `row['candidate_sha256'] not in (PIN, REFERENCE)`. The same mutation should also give the same hash on both architectures; it does today.
   - Model: `model_sha256==MODEL_ORIGINAL` exactly when `mutation=='original'`, and otherwise `model_sha256 not in (MODEL_ORIGINAL, MODEL_PATCHED)`.
3. **Negative-control mode.** Every negative in both files is `-Xint`, but the tuple-set checks ignore mode. Add `row['mode']=='-Xint'` if that's intended.
4. **Final `limits` list.** It's missing items the preference record lists itself: no atomic replace, fsync or encryption; original truncation on serialization failure still happens; concurrent filesystem attackers and JVM exhaustion aren't qualified; `-Xcomp` was requested only, not confirmed. The preference and model identity hashes (entry, helper, original and patched) also appear only indirectly, through `records`.
5. **Minor:**
   - `unit_stderr_sha256` in each boundary file is unbound.
   - Lines 112 and 114 repeat the same check.
   - Line 125's `sys.executable` equality is brittle if the interpreter is reached through a different path. It fails safely.
