**6. AcpxConnection keeps a half-open connection after a setup failure.**
- [O] `AcpxConnection.createConnection` stores the new `HttpConnection` before calling `open()` (javap lines 29512-29525). Inside `send()`, this call sits outside the try block.
- [O] After a failed `open()`, the next `send()` calls `HttpConnection.setTimeout(t)`. If `t` is not 30000, that dereferences a null `socket` and throws a `NullPointerException`.
- [I] This already happened when the Socket constructor failed. Setup failure is now a second way into that state, because the original code published the socket even when `setSoTimeout` failed. The "custom timeout/reconnect" coverage in `INTENDED-CHANGE.md` is at the `HttpConnection` level only, not this `AcpxConnection` sequence. Characterize it or list it as a limit.

## Verified as sound

- **Failure containment** [O]
  - The socket is assigned to the field only after `open()` returns. A failed setup leaves `socket` and `connected` unchanged.
  - Setup failure closes the socket best effort and discards any exception from `close()`.
  - `SecurityException` and `Error` pass through unchanged, and other `RuntimeException`s become a fixed `IOException`.
  - The `timeout<=0` guard can't be reached from original callers: the field starts at 30000, `setTimeout` maps 0 to 30000, and a negative value throws before the field is assigned.
  - [O] `doConnect` catches `IOException` across `new AcpxConnection` (exception table row `415 497 498`) and wraps it as `ConnectException(getMessage())`, so the user sees "Connection setup failed".
  - [I] The run/dispatch classification is unchanged, because the fixed message never starts with "PropertyListException".
- **Publication ordering** [O] The new bytecode is `aload_0, aload_0, getfield host, aload_0, getfield timeout, invokestatic #202, putfield socket, return`, with `stack=3, locals=2`, no exception table and no attributes.
  - [I] One small ordering difference: `timeout` is now read before the blocking DNS/TCP connect, where the original read it afterwards. This matters only if another thread calls `setTimeout` mid-connect, and that already hit a null socket in the original.
- **Exception types** [O]
  - The `instanceof` order in `fixed()` is correct.
  - Casting to `InterruptedIOException` is safe, because the result is only that type when the input was.
  - The constructor-path classes are checked by exact class equality for all eight types.
  - `PortUnreachableException` and similar subclasses map to `SocketException`, as documented.
- **Helper linkage** [O]
  - The five pool entries appended at 198-202 reuse `#100 "open"`.
  - The helper is class version 52 and is called from a version-47 class.
  - All fixture runs used `-Xverify:all`.
  - The helper compiled standalone is byte-identical to the shipped copy, using JDK 1.8.0_362, so there is no bootclasspath warning.
  - `check_security` verifies the helper's strings and the absence of `getMessage`, `initCause` and `addSuppressed`.
  - The development security record says `independent_preservation: PASS`, and its stderr is empty.
- **Exact original class preservation** [O]
  - `plan()` is pinned to the original hash, and `normalize()` reconstructs the whole original class and checks it against that hash.
  - The gate requires the reference and candidate entries to differ only in `HttpConnection`, and requires the reference `HttpConnection` to equal the original.
  - The single-bit mutation test covers the constant pool, Code attributes and members.
  - `transform()`/`TARGETS` are unchanged, and `HttpConnection` exists only in `CURRENT_TARGETS`.
  - Development builds 1 and 2 have the same JAR hash, and the security pin `5e8690…` matches the gate's product hash.
- **Fixture independence, class origins, network and secrets** [O]
  - `FixtureIdentity` checks each listed class's code source and bytes before any guard is installed.
  - The shadowing check rejects fixture class names that exist in the JAR, and fixtures come after the JAR on the classpath.
  - The publication fixture uses only an in-memory `SocketImpl` with the literal `127.0.0.1`; reads and writes are asserted forbidden.
  - The direct fixture's `Fake` overrides every call that would reach native code.
  - With validation removed, `open("must.not.resolve.invalid", …)` would be blocked by `OfflineGuard.checkConnect` before any lookup.
  - `user.home` is a temp directory, and no profiles or credentials are used.
