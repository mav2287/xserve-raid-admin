## Blocking flaws

1. **The integrated build path can't succeed.**
   - `tools/baseline.py:34` doesn't include `com/apple/xsr/som/RaidSystem.class` in `ALLOWED_JAR_CHANGES`, and nothing in the builder calls `model_diagnostic_patch`.
   - A build that contains the change fails `check_artifact` (`verify_builds.py:35`). A build without it fails `check_model_diagnostic.py:47`.
   - **Fix:** apply `plan()` in the builder and add `ENTRY` to the allowlist. Then regenerate `audit/expected-build.json` from a clean commit.
   - **Version conflict:** line 47 requires the built JAR to be byte-identical to "audit25 plus this one entry". If the build bumps `VERSION` or `MANIFEST.MF` (for example to audit26), that check fails by design. Decide which you want, then pin it.

2. **Other gates' comparators will break after integration.**
   - `check_socket_configuration.py:64`, `check_connection_publication.py:35`, `check_stop_admission_experiment.py:34` and `stop_admission_fixtures.py:35` all compare `help_patch.strip_entries(new)` against the reference.
   - Once `RaidSystem` changes, those comparisons will fail unless they also run `model_diagnostic_patch.strip_entries`.

3. **The working tree isn't committed.** All five reviewed files are untracked, so clean qualification (`check_model_diagnostic.py:37`) can't run until they're committed.

There are no blocking flaws in the patch itself or in the overlay gate's logic.

## Limitations (record these; they don't block)

- **Constructor bypass:** `Unsafe.allocateInstance` skips constructors. `agent`, `comms`, `messageFactory`, `eventLog`, `listenerList` and the timer are null, and setting `obs` and the maps by hand stands in for constructor state. That is acceptable only because `paramString` doesn't read any of those fields, which I confirmed at `:5695-6205`. The copy constructor and `setMonitoringPassword` aren't executed; only the javap equality covers them.
- **No runtime `VerifyError` control:** the `#1184` mutant is rejected only by the Python tests, so verification of child-defined classes rests on the JVM spec, not on observed evidence.
- **Negative control coverage:** every mutant stops at the first case in `main:85`, so no control ever reaches the product-loader phase. All four mutants also produce byte-identical stderr; only their input hashes tell them apart. The negative-control records don't store their JVM argv.
- **Gate-level gaps:**
  - `check_artifact` runs only at the start; after the run, only the JAR is rechecked.
  - `candidate_source_commit` isn't compared with `source_commit`. Today the build's recorded input hashes stand in for that link.
- **Unit test runtime:** the per-byte test does about 30k `normalize` calls (the class is 30,021 bytes) against a 120 s timeout. The earlier development run passed, but there isn't much headroom.
- **Unchanged from before:** x64 runs under Rosetta, and `-Xcomp` is only requested, never confirmed.
