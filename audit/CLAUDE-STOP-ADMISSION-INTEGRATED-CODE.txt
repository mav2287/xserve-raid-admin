## What checks out

- **Layout:**
  - `644: goto_w 709`.
  - The 17-byte tail is `aload_0; getfield #11; ifne 280; aload_0; iconst_1; putfield #414; goto_w 649`, ending at 726.
  - Exactly four handler rows are appended for 709–726, mirroring the 644–660 handlers. The handler count goes from 24 to 28.
  - Pool (433), fields and methods are unchanged, and `stack=6, locals=9` is unchanged.
- **Reversal:** `normalize` restores the exact pinned predecessor and requires `plan(restored)==data`.
- **Javap gate:** it pins the reference text, compares the whole pool and identity, and checks every instruction and handler row. The unit test has mutants for `ifne`, the field ref, the `putfield` and the jump target.
- **Stop path is safe to send regardless of the flag.**
  - `stopped` is volatile (javap line 465).
  - Offset 280 builds the original −102 `CommShutdownException` response, and only the guard path skips the `connectionFailureSent` check.
  - A duplicate delivery is prevented because `doConnect` clears `workerActiveTxn` before its callback (line 756), and delivery at 660 requires `workerActiveTxn != null`. `workerActiveStarted` stays false on the stop path.
- **Hooks:** the admission hook replaces `isStopped` at offset 235. The exposure hook pauses *before* the guard read in the guarded variant. Both reverse byte-for-byte and change only the Manager entry.
- **Vector count:** 11 scenarios × 2 policies × 2 architectures × 2 execution modes = 88, of which 44 are Xcomp. Each Xcomp run requires an installed `dispatchLoop` nmethod and no compile failure.

## Residual (as documented, not a defect)

There is still a race between the read at offset 710 and `AcpxConnection.send` at 255: a stop that lands in that window still sends. The guard narrows the window rather than cancelling sends. Nothing here supports release, hardware, native GUI, whole-app compiled or controller qualification.
